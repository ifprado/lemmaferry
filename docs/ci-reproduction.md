# CI and clean-checkout reproduction

The [workflow](../.github/workflows/ci.yml) runs on pushes to `main`, pull
requests, and manual dispatch. Python 3.10 and 3.12 each run the complete unit
suite and both artificial alignment seeds. A separate Python 3.12 job installs
the pinned Lean toolchain and checks 20 generated examples per split: 60
examples, 120 proof declarations, and 120 recognized zero-axiom audits.

Actions are pinned to full commit SHAs resolved from their official upstream
repositories. The workflow uses read-only repository permissions, disables
persisted checkout credentials, and runs Bash with pipeline failure propagation
so logging through `tee` cannot hide a failed command. This follows GitHub's
[action pinning guidance](https://docs.github.com/en/actions/reference/security/secure-use#using-third-party-actions).

The [first hosted run](https://github.com/ifprado/lemmaferry/actions/runs/39009396369)
passed both Python jobs but stopped after Lean installation because
`lean-action` requires a Lake manifest even when package builds are disabled.
The committed dependency-free `lean/lake-manifest.json`, generated by pinned
`lake update`, supplies the missing metadata. This failure does not invalidate
the separately recorded local compiler audits.

The [corrected hosted run](https://github.com/ifprado/lemmaferry/actions/runs/39009649778)
passed at commit `3e6d3704d98473b4d28d76e628aaa3df905772b8`: 28 tests
on each Python version, plus 60 examples and 120 recognized real Lean audits
on Linux. Its downloaded evidence was independently inspected and all 16
recorded hashes matched artifacts or the exact committed source. The retained
[inspection summary](../artifacts/hosted-ci/summary.json) identifies the full
local log and artifact paths.

After compilation, [`verify_lean_evidence.py`](../experiments/verify_lean_evidence.py)
independently checks the exact number and order of records, unchanged input
content, compiler-version agreement with `lean/lean-toolchain`, fresh success
statuses for both proofs, and both named audits in a retained log belonging to
this run. It writes `results/ci-lean/evidence.json` with SHA-256 hashes of the
generated JSONL, checked JSONL, audits, compiler version, pin, and relevant
source files. It validates evidence rather than invoking Lean itself.

The `lean-check-results` workflow artifact retains generated inputs, checked
records, compiler logs, version information, and the evidence manifest, including
partial logs after failures. The two `python-check-results-*` artifacts retain
test logs, exact installed environments, and alignment JSON outputs. Artifacts
are workflow outputs, not a replacement for a versioned release snapshot.

## Local commands

From a fresh clone, create an environment and install the CPU package:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python experiments/toy_alignment.py --seed 7 --output runs/alignment-seed7.json
.venv/bin/python experiments/toy_alignment.py --seed 19 --output runs/alignment-seed19.json
.venv/bin/python experiments/generate_logic.py --count 20 --seed 7
mkdir -p results/ci-lean
cd lean
"$HOME/.elan/bin/lean" --version > ../results/ci-lean/lean-version.txt
../.venv/bin/python ../experiments/check_lean.py ../data/generated/train.jsonl --lean "$HOME/.elan/bin/lean" --output ../results/ci-lean/train.checked.jsonl --log-dir ../results/ci-lean/logs/train
../.venv/bin/python ../experiments/check_lean.py ../data/generated/validation.jsonl --lean "$HOME/.elan/bin/lean" --output ../results/ci-lean/validation.checked.jsonl --log-dir ../results/ci-lean/logs/validation
../.venv/bin/python ../experiments/check_lean.py ../data/generated/test.jsonl --lean "$HOME/.elan/bin/lean" --output ../results/ci-lean/test.checked.jsonl --log-dir ../results/ci-lean/logs/test
cd ..
.venv/bin/python experiments/verify_lean_evidence.py --count 20
```

Install Lean first using the [official instructions](https://lean-lang.org/install/manual/)
if `$HOME/.elan/bin/lean` is unavailable. Invoking it from `lean/` selects the
committed toolchain. The commands use new run outputs; the original release's
evidence is retained separately.

Five evidence-validator tests cover complete mock evidence, missing long-proof
audits despite a claimed successful status, altered checked input, insufficient
counts, and the wrong compiler version. Existing checker tests separately cover
missing executables, stale statuses, and exit-zero output without audits.
Unit-test fixtures do not count as real compiler verification.

## Recorded clean checkout

On 2026-10-17 UTC, a fresh clone of the public repository was checked out at
`98cb9eca826de6d955f1a0250140f5505e5ffe35` (the frozen `v0.1.0` baseline).
A new virtual environment installed the CPU package. All 23 baseline tests
passed. Both alignment JSON outputs agreed with the release artifacts using
relative tolerance `1e-10` and absolute tolerance `1e-12`. Regenerating the
60 logic inputs produced byte-identical JSONL to the frozen LF-002 inputs;
real Lean checked all 120 proofs with all 120 zero-axiom audits. The clone's
tracked worktree stayed clean.

The [reproduction summary](../artifacts/clean-checkout-baseline/summary.json),
command logs, compiler audits, environment lock, and SHA-256 manifest are kept
under [`artifacts/clean-checkout-baseline/`](../artifacts/clean-checkout-baseline/).
This reproduces the published baseline locally. The later CI changes add five
evidence-validator tests and the missing Lake manifest; hosted status must be
read from the workflow run for the corresponding commit.

## Constructive-loop branch

`research/constructive-learning-loop` also triggers the workflow directly.
The original Python 3.10/3.12 and Lean jobs remain. A fourth job installs the
optional CPU learning runtime and pinned Lean, runs the complete test suite,
executes two translated-learning iterations with five matched training arms,
and independently verifies the resulting library, maps, targets, evaluation,
initial weights, continued AdamW state, and all checkpoint reloads.

The job uploads `constructive-loop-evidence`, including its environment, tests,
registered protocol, fixed evaluation, proof sources/logs, activation arrays,
maps, and checkpoints. It uses tiny neural fixtures and does not download
pretrained checkpoints. Separate local pretrained-run evidence is retained in
[`artifacts/constructive-loop/`](../artifacts/constructive-loop/).

Run the same checks locally with the commands in the
[constructive-loop protocol](constructive-loop.md). Read hosted status from the
run for the exact branch commit; baseline success alone does not validate a
later refactor.
